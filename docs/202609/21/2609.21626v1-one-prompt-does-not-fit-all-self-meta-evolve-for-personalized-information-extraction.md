## 摘要
大型语言模型（LLM）正日益被部署于企业信息抽取（IE）任务中，而在这些场景下，同一份文档必须针对不同用户以不同方式重新组织。然而，现有的提示优化方法依赖于针对全局目标优化的单一提示，这与真实工作场景中固有的用户异质性并不一致。我们将企业信息抽取形式化为交互反馈下的逐用户提示适配问题，并提出 Self-Meta-Evolve，一个分层框架：它为每个用户维护专属提示，并通过双循环过程持续改进该提示——内循环基于人物角色条件化的反馈来编辑结构化提示，外循环则通过蒸馏成功的编辑模式来演化元提示本身。为实现可扩展的训练与评估，我们发布了一个由人物角色驱动的信息抽取基准，包含 292 个模拟企业用户，并配套一个基于 O*NET 职业分类体系、可复现的人物角色生成流程。在该基准上，Self-Meta-Evolve 达到了 74.58% 的成功率，比最强的提示优化基线高出 13.56 个绝对百分点，并且仅需两次迭代即可达到 52.54%。一项由二十位真实专业人士参与的双盲人类研究进一步证实，在 71% 的成对比较中，经我们框架适配的提示优于静态基线。

## Abstract
Large language models (LLMs) are increasingly deployed for enterprise information extraction (IE), where the same document must be reorganized differently for each user. Existing prompt optimization methods, however, rely on a single prompt optimized against a global objective, which is misaligned with the inherent user heterogeneity of real workplaces. We formulate enterprise IE as per-user prompt adaptation under interaction feedback and propose Self-Meta-Evolve, a hierarchical framework that maintains a dedicated prompt for each user and continuously refines it through a dual-loop process: an inner loop that edits structured prompts based on persona-conditioned feedback, and an outer loop that evolves the meta-prompt itself by distilling successful editing patterns. To enable scalable training and evaluation, we release a persona-driven IE benchmark of 292 simulated enterprise users, paired with a reproducible persona-generation pipeline grounded in O*NET occupational taxonomies. On this benchmark, Self-Meta-Evolve achieves a 74.58% success rate, outperforming the strongest prompt-optimization baseline by 13.56 absolute points, and reaches 52.54\% within only two iterations. A double-blind human study with twenty real professionals further confirms that prompts adapted by our framework win against static baselines in 71% of pairwise comparisons.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 已成为企业数据流水线的核心组件，用于将邮件、会议记录、项目报告等非结构化材料转化为结构化表示。提示（prompt）是控制这类系统的"事实接口"，但现有平台普遍采用"一个精心设计的提示服务所有用户"的范式。
- **核心矛盾**：企业用户具有高度异质性。同一封项目状态邮件，项目经理关注可执行的截止日期与责任人，财务分析师则需要细粒度预算实体与风险指标。论文的 50 人内部调研显示，**72% 的用户会例行对通用 LLM 输出进行后期编辑**以符合本角色标准。
- **理论视角**：工作重塑理论（Job Crafting）与工作设计理论指出，有效工具必须与员工动态塑造的角色需求对齐，静态全局提示无法满足这一属性。
- **现有方法的错配**：无论是搜索式（APE、OPRO）、梯度启发式（ProTeGi）、进化式（EvoPrompt、Promptbreeder）还是多智能体变体（MAPRO），都共享同一假设——**针对固定数据集和全局目标优化单一提示**。这与"正确答案取决于阅读者是谁"的用户中心信息抽取根本冲突。
- **问题形式化**：论文将企业 IE 重新定义为**交互反馈下的逐用户提示适配（per-user prompt adaptation under interaction feedback）**：每个用户拥有专属提示，由用户特定的批判信号驱动其随时间演化。

## 2. 方法论

### 2.1 核心思想
- 采用**分层（hierarchical）双循环**结构：
  - **内循环**：基于人物角色条件化的反馈，对单个用户的结构化抽取提示进行编辑。
  - **外循环**：通过蒸馏跨用户的成功编辑轨迹，演化控制这些编辑的**元提示（meta-prompt）**。
- 两条设计依据：① 现代 LLM 具有较强的角色扮演保真度，可扩展地模拟多样化用户人设与反馈；② 提示优化天然可分解为"对任务提示的低层编辑"与"决定如何编辑的高层元策略"两个层级。

### 2.2 问题建模与损失函数
- 设用户人设分布 $u \sim P_U$，每个 $u$ 编码角色描述、文档分布 $D_u$ 与信息偏好画像。目标是求解：
  $$p^*_u = \arg\min_{p \in P} \mathbb{E}_{x \sim D_u}[L(p; u, x)]$$
- **AI User 反馈模型**：以 LLM 扮演用户 $u$，输出结构化反馈 $F_\phi(u, x, y) = \{(a_i, t_i)\}$，其中 $a_i$ 为抽取到的条目，$t_i \in \{\text{revise}, \text{delete}\}$ 表示用户会采取的动作。
- **标量损失**：$L = \lambda_r N_{\text{revise}} + \lambda_d N_{\text{delete}}$。通过 5 名企业用户对 30 个样本的 1–5 Likert 量表标注，测得删除相对修改的努力比约为 2.04 ± 0.41，据此设定 $\lambda_d = 0.2 = 2\lambda_r$。
- **成功阈值 $\tau$**：取最强基线 ProTeGi 在 50 个人设开发集上的中位部署损失，归一化为 $\tau = 0.75$，并在所有方法中统一复用。

### 2.3 结构化提示表示
- 将提示表示为类 JSON 对象，键为功能分区：**任务描述、抽取指令、输出模式、示例、约束规则**。
- 每个分区由稳定的 `point_id` 标识，使优化器能**定位单个 point 而非重写整个提示**，提升更新稳定性与可解释性。

### 2.4 内循环：人设条件化编辑
- 在第 $t$ 步，采样人设 $u$ 与文档 $x$；当前提示 $p_t$ 产生输出 $y_t = f_{\text{LLM}}(x, p_t)$。
- AI User 返回反馈 $S_t = F_\phi(u, x, y_t)$；由元提示 $\pi$ 引导的 LLM 编辑代理提出编辑计划 $E_t = f_{\text{LLM}}(p_t, S_t; \pi)$，定位具体的 `(section, point_id)` 对。
- 新提示：$p_{t+1} = \text{ApplyEdits}(p_t, E_t)$。
- 若损失下降，则将轨迹 $(p_t, S_t, E_t)$ 追加到**成功缓冲区 $B$**。
- **示例**：某 DevOps Lead 人设要求"可执行的值班跟进"。初始提示同时抽取跟进事项与团队公告，AI User 标记公告为 delete；内循环定位到 `instr.scope` 点，提出 `patch_logic` 动作将范围收窄为"含明确责任人与截止日期的事项"，损失从 1.4 降至 0.6。

### 2.5 外循环：元提示演化
- 当 $|B|$ 达到阈值 $K$ 时，LLM 作为元优化器读取累积的成功轨迹并重写元提示：$\pi' = f_{\text{Meta}}(\pi, B)$。
- 直觉：捕获可跨用户泛化的编辑模式。例如反馈显示过度抽取时，模型倾向对 `instr.scope` 施加 `add_constraint` 而非重写示例。元提示质量以**在留出人设上的适配效率（SR@t）**衡量。
- **算法流程（Algorithm 1）**：初始化 $p_0, \pi, B \leftarrow \emptyset$ → 循环 $T$ 步：采样人设与文档 → 抽取 → 获取反馈 → 生成编辑计划 → 应用编辑 → 若损失下降则入缓冲区 → 每 $K$ 次触发元提示更新。

## 3. 实验设计

### 3.1 数据集与 Benchmark
- **主基准**：**292 个人设驱动的企业 IE 基准**，按 60/20/20 划分训练/开发/评估（固定随机种子）。
- **人物角色生成流水线（4 阶段，可复现）**：
  - **Stage 1**：从公开的 U.S. O*NET 职业数据库（release 28.0）出发，筛选 SOC 大类 11/13/15/17/19/23/25/27，得到 412 个候选种子角色。
  - **Stage 2**：用 GPT-5.1 将 O*NET 描述扩展为结构化人设 JSON，含角色描述、文档分布、3–6 条信息偏好声明，生成 400 个候选人设。
  - **Stage 3**：三重质控——嵌入余弦相似度去重（>0.92 合并，删 47）、LLM 一致性打分（<4 丢弃，删 38）、偏好具体性（少于 3 条可执行偏好丢弃，删 23），最终保留 **292 个人设**。
  - **Stage 4**：为每个人设合成 8–12 份企业文档（邮件、聊天记录、状态报告），生成器**仅条件于角色与主题域，不接触偏好画像**，避免黄金偏好信号泄漏。
- **额外测试集**：STEM-Personas（N=50，SOC 15/17/19）与 Humanities-Personas（N=50，SOC 25/27 及图书管理员/编辑），与主池不相交。
- **公开文档试点**：CUAD 与 SciREX，各 20 份文档 × 5 个角色条件化抽取目标。
- **数据声明**：所有文档均为 LLM 合成，不含真实企业数据；人设源自公开分类体系；承诺以 CC-BY 4.0 发布人设池、生成文档、AI-User 提示与流水线脚本。

### 3.2 对比方法
- 梯度启发式：**ProTeGi**（beam width 4）
- 搜索式：**APE**（10 候选）、**OPRO**（聚合 top-4 历史提示，每步 4 候选）
- 进化式：**EvoPrompt**（种群 4，标准 NL 交叉/变异）
- 优化专用：**Bandit-UCB**（UCB1，各提示分区为臂）、**MetaSPO**（元系统提示优化）、**Pareto Prompt**（准确率+人设合规双目标 Pareto 前沿）
- 消融基线：**Self-Frozen**（禁用外循环的自身变体）

- **Success Rate (SR)**：部署损失 ≤ $\tau$ 的人设比例。
- **Mean Loss (ML)**：所有人设部署损失均值。
- **SR@t**：前 $t$ 次内循环迭代内的累积成功率，刻画收敛速度。

### 3.4 骨干模型
- 抽取器与 AI User 统一使用 **GPT-5.1**；额外在 GPT-5.5、GPT-4.1、Claude-Opus-4.8、Claude-3.7-Sonnet 上做骨干鲁棒性验证；跨模型判官检验使用 Claude-3.7 与 Qwen-2.5-72B。

- **主结果（RQ1）**：Self-Meta-Evolve 在留出评估集上达到 **74.58% SR**，较最强基线 ProTeGi 高出 **13.56 个绝对百分点**；ML 从 0.7542 降至 0.5122（**−32%**）。**SR@2 = 0.5254** 已超过 OPRO、EvoPrompt、MetaSPO、APE、Pareto Prompt 的最终 SR。
- **骨干鲁棒性**：在 5 种骨干上相对 ProTeGi 提升 **11.87–15.25 个百分点**，结论一致。
- **收敛与效率（RQ2）**：优化轨迹显著更陡；ProTeGi 约在 $t=10$ 平台化，而外循环持续抬高上限。在非平凡优化器中每百分点 SR 的 API 成本最优。
- **跨人设泛化（RQ2）**：多数基线从 STEM 到 Humanities 下降 8.0–16.0 点，Self-Meta-Evolve 将差距收窄至 **4.0 点**，说明元提示内化了跨域编辑原则而非过拟合 STEM 式错误。
- **消融（RQ3）**：移除外循环导致最大 SR 下降（74.6 → 57.6），是后期增益的主要驱动；成功缓冲区与结构化编辑计划格式均贡献早期效率。
- **人设规模**：SR 从 50 到 150 人快速上升（+15.7），200 后进入边际递减，**200–250 人即可支撑稳定元演化**，292 人处于饱和点之上。
- **超参稳健性**：在 $\lambda_d/\lambda_r \in [1.5, 2.5]$ 范围内方法排名保持，SR 波动 <2 点，回应了 2:1 比值"任意性"的质疑。
- **人工验证**：20 位真实专业人士的 200 次成对判断中，适配提示**胜率 71.0%**、负率 19.0%、平局 10.0%（二项检验 p<10⁻⁵）；合成人设与真实 LinkedIn 派生画像在四个维度上差距均 ≤0.06 且无显著差异（p>0.5

（接上）），说明合成人设可作为真实用户画像的可行代理。
- **失败模式分析**：30 个失败人设归纳为三类——① 偏好表述内在矛盾（如同时要求"极简输出"与"完整审计追踪"）；② 文档主题与人设偏好域几乎不重叠（如财务人设收到纯技术日志）；③ 反馈信号稀疏导致编辑计划无的放矢。三类失效均指向"反馈-文档-偏好"三者的可对齐性，而非元演化机制本身失效。

## 7. 方法优点与创新点

- **问题重构的价值**：将企业 IE 从"单提示全局优化"重构为"逐用户提示适配"，切中了 LLM 落地的真实痛点。作者用 72% 后期编辑率这一实证数据锚定动机，而非停留在概念层面。
- **分层双循环设计的合理性**：内循环负责"个性化落地"、外循环负责"跨用户经验蒸馏"，二者分工明确。相比让单一优化器同时兼顾个体与群体，该结构避免了目标冲突。
- **结构化提示表示的工程价值**：以 `point_id` 定位到分区级编辑，使更新可解释、可回滚、可审计，这对企业部署（合规、版本管理）比"整体重写提示"更实用。
- **元提示作为可迁移资产**：外循环产出的元提示本身是跨用户、跨域的复用资产，跨 STEM→Humanities 仅 4.0 点下降是最有力的证据。
- **实验严谨性**：成功阈值由最强基线校准、配对 bootstrap 检验、跨模型判官去偏、双盲人工评估、公开文档外部试点，构成了较完整的验证闭环。

## 8. 局限与不足

- **评估规模**：主评估集 N=59，虽统计检验显著，但对细粒度子群（如按 SOC 大类）的比较能力有限。
- **完全合成数据**：所有企业文档与人设均由 LLM 生成，作者虽以公开文档试点（CUAD/SciREX）作外部校验，但仅为 pilot-scale，且抽取目标由作者设计，真实企业数据的噪声、格式混乱、跨文档指代等挑战未被充分覆盖。
- **成本结构**：方法依赖 GPT-5.1 等闭源 API，API 成本虽在非平凡优化器中最低，但绝对成本（每百分点 SR 约 4.98K tokens × 30 迭代 × 292 人设）在企业规模化部署中仍不可忽视；论文未报告端到端货币成本或延迟。
- **反馈模型的循环性风险**：AI User 与抽取器同为 GPT-5.1，存在"同源偏差"——若抽取器系统性遗漏某类实体，AI User 也可能同样"看不见"该遗漏，导致优化盲区。跨模型判官检验缓解了评估端偏差，但未直接检验反馈端。
- **损失函数的启发式成分**：$\lambda_d = 2\lambda_r$ 来自 5 名用户 × 30 样本的小样本标注，尽管敏感性分析显示排名稳健，但权重本身的普适性仍有待更大样本验证。
- **硬件与工程细节缺失**：无 GPU/推理时延/并发吞吐报告，对需要本地化或私有化部署的读者参考价值有限。
- **元演化的理论刻画不足**：论文以 SR@t 等经验指标衡量元提示质量，但未给出元提示收敛性或泛化界的形式化分析。

## 9. 总体评价与启发

- **定位**：这是一篇问题驱动型工作，核心贡献在于**重新定义问题**（逐用户提示适配）+ **提出可扩展的解法框架**（分层自元演化）。其价值更多体现在范式与工程可落地性，而非单点算法技巧。
- **对研究社区的启发**：
  - 提示优化的下一个前沿可能不是"更强的单提示搜索"，而是"如何让优化器学会优化"——即元层面的策略学习。
  - "AI User 作为反馈源"提供了一条低成本的个性化监督路径，可迁移到推荐、写作助手、代码审查等任何"正确性依赖用户角色"的任务。
  - 结构化、可定位的提示表示或可成为提示工程从"艺术"走向"可维护软件资产"的关键中间层。
- **对工业实践的启发**：企业若要在 LLM 流水线上实现角色化抽取，可优先采用"分区提示 + 逐用户编辑轨迹 + 周期性元策略刷新"的架构；人设池规模在 200–250 即可进入稳定收益区，无需盲目扩张。
- **尚待回答的问题**：当用户偏好随时间漂移（概念漂移）时，元提示是否需要遗忘机制？当反馈来自真实用户且极其稀疏时，AI User 模拟的保真度如何维持？多用户偏好冲突（如同一文档服务多个下游消费者）时，逐用户提示如何协同？这些问题为后续研究留下了明确接口。
